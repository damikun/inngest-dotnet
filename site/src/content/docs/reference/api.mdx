Every public type of the SDK, grouped by what it is for. The guides explain how to use them; this page is for
looking things up. Types are in the `Inngest` namespace unless noted.

`AddInngest` also registers `IInngestClient`, `IInngestRunsClient` and `IInngestRealtime`, and `IStepTools`, which
resolves to the steps of the durable endpoint or function that is running.

## Options

**`InngestOptions`**: `AppId`, `AppVersion`, `EventKey`, `SigningKey`, `SigningKeyFallback`, `Environment`,
`IsDev`, `DevServerUrl`, `BaseUrl`, `ApiBaseUrl`, `EventApiBaseUrl`, `ServeOrigin`, `ServePath`, `AllowInBandSync`,
`AllowUnsignedSync`, `Streaming`, `SessionPropagation`, `Checkpointing`, `SerializerOptions`. See
[Configuration](/inngest-dotnet/guides/configuration/).

**`ConnectOptions`**: `InstanceId`, `MaxWorkerConcurrency`, `GatewayUrl`. See [Connect](/inngest-dotnet/guides/connect/).

**`InngestHealthCheckOptions`**: `RequireEventKey`, `CheckSync`, `CacheDuration` (30 seconds) and `FailureCacheDuration`
(5 seconds). See [Health checks](/inngest-dotnet/guides/deploying/#health-checks).

**`FunctionOptions`**, an immutable record:

| Property | Type |
|---|---|
| `Id` (required) | `string` |
| `Name` | `string?` |
| `Triggers` (required) | `IReadOnlyList<FunctionTrigger>` |
| `Retries` | `int?` |
| `Concurrency` | `IReadOnlyList<ConcurrencyLimit>?` |
| `Throttle`, `RateLimit`, `Debounce`, `BatchEvents`, `Priority` | records of the same names |
| `Idempotency` | `string?` |
| `CancelOn` | `IReadOnlyList<CancelOn>?` |
| `Timeouts` | `FunctionTimeouts?` |
| `Singleton` | `Singleton?` |
| `Middleware` | `IReadOnlyList<FunctionMiddleware>?`; see [Middleware](#middleware) |
| `Checkpointing` | `CheckpointingOptions?` |

The flow control records and their constructor arguments and properties:

| Record | Constructor | Properties |
|---|---|---|
| `ConcurrencyLimit` | `(int Limit)`; 0 means no limit | `Key`, `Scope` (`ConcurrencyScope.Function`, `Environment`, `Account`) |
| `Throttle` | `(int Limit, TimeSpan Period)` | `Burst`, `Key` |
| `RateLimit` | `(int Limit, TimeSpan Period)` | `Key` |
| `Debounce` | `(TimeSpan Period)` | `Key`, `Timeout` |
| `BatchEvents` | `(int MaxSize, TimeSpan Timeout)` | `Key`, `If` |
| `Priority` | `(string Run)` | |
| `CancelOn` | `(string Event)` | `If`, `Match`, `Timeout` |
| `FunctionTimeouts` | | `Start`, `Finish` |
| `Singleton` | `(SingletonMode Mode)` | `Key`; modes `Skip` and `Cancel` |

**Triggers**: `Trigger.Event(string name, string? @if = null)` and `Trigger.Event<T>(string? @if = null)`, for a
typed event `T`, return an `EventTrigger`. `Trigger.Cron(string schedule, string? timezone = null)` and
`Trigger.Cron(string schedule, TimeSpan jitter, string? timezone = null)` return a `CronTrigger`, whose `Jitter`, from
1 second to 5 minutes, starts each scheduled run up to that much later. `EventTrigger` and `CronTrigger` derive from
`FunctionTrigger`. `CancelOn.For<T>()` returns a `CancelOn` for a typed event.

**`CheckpointingOptions`**, a record. Checkpointing runs the steps of a function one after another in the same call
from Inngest and saves each to Inngest as it completes, instead of ending the call after every step. It is off by
default. `InngestOptions.Checkpointing` sets it for every function, and `FunctionOptions.Checkpointing`, which wins
over it, for one function.

| Property | Default | Meaning |
|---|---|---|
| `Enabled` | `true` | `false` turns checkpointing off for one function when the app turns it on. |
| `MaxRuntime` | null: 10 seconds for the serve endpoint, 5 minutes for Connect workers | How long one call may keep running steps. `Timeout.InfiniteTimeSpan` removes the limit. |
| `BufferedSteps` | `1` | How many completed steps are saved to Inngest together. |
| `MaxInterval` | null | The longest a completed step waits to be saved while `BufferedSteps` is not reached; null waits until the buffer is full or the call ends. |

## Attributes

Each sets the `FunctionOptions` member of the same name; durations are time strings such as `"30s"` or `"1h30m"`.
`AddFunction<TFunction>()` reads them when the app starts: it starts from `[InngestFunction]` and applies the others,
which derive from `FunctionOptionsAttribute`, in ascending `Order`, then in the order they are declared.

| Attribute | Constructor | Properties |
|---|---|---|
| `InngestFunctionAttribute` | `(string id)` | `Name`, `Retries`, `Idempotency` |
| `EventTriggerAttribute`, `EventTriggerAttribute<T>` | `(string name)`, `()` | `If`; repeatable |
| `CronTriggerAttribute` | `(string schedule)` | `Timezone`, `Jitter`; repeatable |
| `ConcurrencyAttribute` | `(int limit)` | `Key`, `Scope`; repeatable |
| `ThrottleAttribute` | `(int limit, string period)` | `Burst`, `Key` |
| `RateLimitAttribute` | `(int limit, string period)` | `Key` |
| `DebounceAttribute` | `(string period)` | `Key`, `Timeout` |
| `BatchEventsAttribute` | `(int maxSize, string timeout)` | `Key`, `If` |
| `PriorityAttribute` | `(string run)` | |
| `SingletonAttribute` | `(SingletonMode mode)` | `Key` |
| `CancelOnAttribute`, `CancelOnAttribute<T>` | `(string name)`, `()` | `If`, `Match`, `Timeout`; repeatable |
| `TimeoutsAttribute` | | `Start`, `Finish` |
| `FunctionOptionsAttribute` | | `Order`; `Apply(FunctionOptions)` returns the options with the attribute applied. Derive from it and override `Configure(FunctionOptions)` for an attribute of your own. |

The generic forms take the event's name from `T`, which implements `IInngestEventData`.

## Steps

**`IStepTools`**, the type of `context.Step`:

| Method | Returns |
|---|---|
| `RunAsync<T>(string id, Func<CancellationToken, Task<T>> handler)` | `Task<T>` |
| `SleepAsync(string id, TimeSpan duration)` | `Task` |
| `SleepUntilAsync(string id, DateTimeOffset until)` | `Task` |
| `WaitForEventAsync<TData>(string id, WaitForEventOptions options)` | `Task<InngestEvent<TData>?>` |
| `InvokeAsync<TResult>(string id, InvokeOptions options)` | `Task<TResult>` |
| `SendEventAsync(string id, IReadOnlyList<InngestEvent> events)` | `Task<SendEventsResult>` |
| `InvokeAsync<TFunction, TResult>(string id, object? data = null, TimeSpan? timeout = null)` | `Task<TResult>`; runs the function registered as `TFunction`, which must return a `TResult` |
| `WaitForSignalAsync<TData>(string id, WaitForSignalOptions options)` | `Task<InngestSignal<TData>?>`; null when the timeout passes first |
| `SendSignalAsync(string id, InngestSignal signal)` | `Task<string?>`: the id of the run the signal resumed, or null when no run waits for it |
| `FetchAsync(string id, HttpRequestMessage request)` | `Task<HttpResponseMessage>`; Inngest makes the request, and the response is memoized |
| `InferAsync<TResponse>(string id, InferOptions options)` | `Task<TResponse>`; Inngest sends the request to the AI provider, and the response is memoized |
| `AIWrapAsync<TInput, TResult>(string id, TInput input, Func<TInput, CancellationToken, Task<TResult>> handler)` | `Task<TResult>`; runs your own model call like a run step that the Inngest UI shows as one, with the input; a rerun with an input edited there passes the edited input |
| `PublishAsync<T>(string id, RealtimeTopic topic, T data)` | `Task<T>`; publishes a [realtime](#realtime) message once, tagged with the run; also for a `RealtimeTopic<T>` |
| `PublishStreamAsync(string id, RealtimeTopic topic, IAsyncEnumerable<string> chunks)` | `Task<string>`; streams the text to the topic as it arrives and memoizes all of it, so a replay does not read the chunks again |
| `ParallelAsync<T>(ParallelMode mode, Func<Task<T>> steps)` | `Task<T>`; runs the callback with the mode applied to every step it creates |

The members after the first six have default implementations, so a fake only has to implement the six. The defaults
of `InvokeAsync<TFunction, TResult>`, `WaitForSignalAsync`, `SendSignalAsync`, `FetchAsync`, `InferAsync`,
`AIWrapAsync`, `PublishAsync` and `PublishStreamAsync` throw `NotSupportedException`. Every method but `ParallelAsync` also has an overload that takes a `StepOptions` in place of
the id.

`StepToolsExtensions` adds `RunAsync` overloads for handlers that take no token, return no value or are
synchronous, a non-generic `WaitForEventAsync` that returns `JsonElement` data, and `SendEventAsync` for a single
event. For a typed event `T` it adds `WaitForEventAsync<T>(string id, TimeSpan timeout, string? match = null,
string? @if = null)` and `SendEventAsync<T>` for one `T` or several. It also adds a non-generic `WaitForSignalAsync`
with `JsonElement` data, an `InferAsync` that returns `JsonElement`, an `AIWrapAsync` whose handler takes no token,
and `ParallelAsync(ParallelMode, Func<Task>)` for steps without a result. These methods also take a `StepOptions` in place of the id, except `ParallelAsync`.

| Record | Constructor | Properties |
|---|---|---|
| `StepOptions` | `(string Id)` | `Name`, shown in the Inngest UI; `ParallelMode`, for this step instead of the mode of an enclosing `ParallelAsync`. A `string` converts to it implicitly. |
| `WaitForEventOptions` | `(string Event, TimeSpan Timeout)` | `Match`, `If` |
| `InvokeOptions` | `(string FunctionId)` | `AppId`, `Data`, `User`, `Timeout`, `Meta`, the sessions of the invoked run |
| `WaitForSignalOptions` | `(string Signal, TimeSpan Timeout)` | `OnConflict`: `SignalConflict.Fail`, the default, fails the run when another run already waits for the signal; `Replace` takes the signal over |
| `InngestSignal` | `(string Name, object? Data = null)` | A signal to send. |
| `InngestSignal<TData>` | `(string Name, TData Data)` | A signal as the waiting run receives it. |
| `InferOptions` | `(AIFormat Format, Uri Url, object Body)` | `AuthKey`, `Headers` |

`ParallelMode` is `Wait`, the default, where Inngest calls the function again once all the steps started together
have finished, or `Race`, where it calls the function again each time one of them finishes. See
[Parallel steps](/inngest-dotnet/guides/parallel-steps/). `AIFormat` names the provider API: `OpenAIChat`,
`OpenAIResponses`, `Anthropic`, `Gemini`, `Grok` or `AzureOpenAI`.

## Runs

**`IInngestRunsClient`** reads and cancels runs through the Inngest REST API, with the app's signing key:

| Method | Returns |
|---|---|
| `GetRunAsync(string runId, CancellationToken)` | `Task<FunctionRun>`: the run's status and, once it has ended, its output |
| `GetEventRunsAsync(string eventId, CancellationToken)` | `Task<IReadOnlyList<FunctionRun>>`: the runs an event started, by the event id that sending it returned |
| `CancelRunAsync(string runId, CancellationToken)` | `Task`; a step that is running finishes, and no further steps run |

**`FunctionRun`**, a record: `RunId`, `Status`, `FunctionId` (Inngest's own id of the function, a UUID),
`FunctionVersion`, `StartedAt`, `EndedAt`, `EventId`, `BatchId`, `OriginalRunId`, `Cron`, `EnvironmentId`, `Output`
and `GetOutput<T>()`, which reads the output with the app's serializer options. `Status` is a `FunctionRunStatus`:
`Unknown`, `Scheduled`, `Running`, `Completed`, `Failed` or `Cancelled`.

Inngest caches these answers for a few seconds, a run for 3 and the runs of an event for 15, and only `EndedAt` says
for sure that a run is over. Failures throw `InngestException` with Inngest's message.

## Realtime

**`IInngestRealtime`** publishes, streams and receives realtime messages and mints subscription tokens through the
Inngest API, with the app's signing key. See [Realtime](/inngest-dotnet/guides/realtime/).

| Method | Returns |
|---|---|
| `PublishAsync<T>(RealtimeTopic topic, T data, CancellationToken)` | `Task`; publishes at once, tagged with the run when called inside one. Text goes out as it is, anything else as JSON. Also for a `RealtimeTopic<T>`. |
| `PublishStreamAsync(RealtimeTopic topic, IAsyncEnumerable<string> chunks, CancellationToken)` | `Task<string>`: all the text, streamed to the topic in one request as it arrives |
| `SubscribeAsync<T>(RealtimeTopic<T> topic, CancellationToken)` | `IAsyncEnumerable<RealtimeMessage<T>>`: the topic's messages from now on, with the data read as a `T` |
| `SubscribeAsync(string channel, IReadOnlyList<string> topics, CancellationToken)` | `IAsyncEnumerable<RealtimeMessage<JsonElement>>` for several topics of a channel |
| `GetSubscriptionTokenAsync(string channel, IReadOnlyList<string> topics, CancellationToken)` | `Task<RealtimeToken>` for a browser to subscribe to these topics of the channel |

**`RealtimeTopic`**, a record `(string Channel, string Name)`, and **`RealtimeTopic<T>`**, the same for data of type
`T`, with `Untyped` for the members that take any topic. **`RealtimeMessage<T>`**, a record `(RealtimeMessageKind Kind,
string Channel, string Topic)` with `Data`, `StreamId`, `Text`, `RunId` and `CreatedAt`; `RealtimeMessageKind` is
`Data`, `StreamStart`, `StreamChunk`, `StreamEnd`, `Run` or `Other`. **`RealtimeToken`**, a record `(string Channel,
IReadOnlyList<string> Topics, string Key)` with `ApiBaseUrl`; serialized with camelCase names, it is the token object
that `useRealtime` and `subscribe` of the TypeScript SDK take.

## Durable endpoints

Package `Inngest.AspNetCore`. The API is marked `[Experimental("INNGEST001")]`, because Inngest calls durable endpoints
beta; [Durable endpoints](/inngest-dotnet/guides/durable-endpoints/#beta) shows how to suppress the diagnostic.

**`DurableEndpointOptions`**, the argument of `WithDurableEndpoint`:

| Property | Type | Default |
|---|---|---|
| `Id` | `string?` | The method and the route pattern, such as `POST /orders/{id}` |
| `Retries` | `int?` | 3 |
| `AsyncResponse` | `DurableEndpointResponse` | `Redirect` |
| `RedirectUrl` | `Func<DurableEndpointRun, Uri>?` | The output URL on the Inngest API |
| `MaxRequestBodySize` | `int` | 1 MiB; a larger request gets 413 |

**`DurableEndpointResponse`** is what the client gets when Inngest takes the run over: `Redirect`, a 303 to the URL that
answers with the endpoint's response, or `Token`, a 200 with `{"run_id", "token"}`. **`DurableEndpointRun`**, a record
`(string RunId, string Token)`, is what `RedirectUrl` receives.

**`DurableEndpointAttribute`** marks a controller or an action, as `WithDurableEndpoint` does for a minimal API
endpoint. Its constructor is `(string? id = null)`, and its properties are `Retries`, where a negative number means the
default, and `AsyncResponse`. **`DurableEndpointDiagnostics.Id`** is `"INNGEST001"`, the diagnostic that marks the API.

## Errors

| Exception | Meaning |
|---|---|
| `NonRetriableException` | Thrown by your code to fail a step or run without retrying. |
| `RetryAfterException` | Thrown by your code to retry after `Delay` or at `RetryAt`. |
| `StepFailedException` | Thrown by the SDK where a step that failed for good is awaited: `StepId`, `Error`. When the recorded error has a cause, `InnerException` is a `FunctionErrorException` for it. |
| `FunctionErrorException` | An error Inngest recorded, rebuilt as an exception: `Error` holds the recorded name, message and stack, and `InnerException` the recorded cause. |
| `InngestException` | Thrown by the SDK when talking to Inngest fails, with `StatusCode` when there is one. |

## Middleware

`InngestMiddleware` has virtual hooks that do nothing by default: `OnRunStartAsync`, `OnMemoizationEndAsync`,
`OnRunCompleteAsync`, `OnRunErrorAsync`, `OnStepStartAsync`, `OnStepCompleteAsync`, `OnStepErrorAsync`,
`WrapFunctionAsync`, `WrapStepAsync`, `WrapStepHandlerAsync` and `WrapSendEventAsync`. `StepInfo` describes a step:
`Id`, `HashedId`, `Type`, `Memoized`, and `Name`, the display name the code gave it. `Type` is a `StepType`: `Run`,
`Sleep`, `WaitForEvent`, `Invoke`, `SendEvent`, `WaitForSignal`, `SendSignal`, `Fetch`, `AIInfer`, `AIWrap` or
`RealtimePublish`. See
[Middleware](/inngest-dotnet/guides/middleware/).

**`FunctionMiddleware`** is middleware for one function, listed in `FunctionOptions.Middleware`. It runs inside the
app's middleware, also for the function's failure handler. `FunctionMiddleware.Of<TMiddleware>()` resolves
`TMiddleware` from the call's scope and registers it as scoped unless the app registered it;
`FunctionMiddleware.Of(Func<IServiceProvider, InngestMiddleware>)` calls the factory with the call's scope on every
call.

**`IPayloadTransform`**, implemented by a middleware, rewrites the raw JSON between Inngest and the function:

| Method | Rewrites |
|---|---|
| `TransformEvent(JsonElement @event, Utf8JsonWriter writer)` | A triggering event, before the function's event type is read from it |
| `TransformStepResult(FunctionContext context, StepInfo step, JsonElement result, Utf8JsonWriter writer)` | A memoized result of any step type, before the step's result type is read from it |
| `TransformStepOutput(FunctionContext context, StepInfo step, JsonElement output, Utf8JsonWriter writer)` | What a step handler returned, before Inngest memoizes it |
| `TransformFunctionOutput(FunctionContext context, JsonElement output, Utf8JsonWriter writer)` | The function's output, before it is sent to Inngest |

Each method writes one replacement value and returns `true`, or writes nothing and returns `false` to keep the value;
the defaults keep every value. JSON coming in reaches the transforms in registration order, and JSON going out in
reverse order.

## Connect

Package `Inngest.Connect`. `AddConnect` registers **`IInngestConnection`**, the worker's connection to Inngest:
`State`, and `WaitForStateChangedAsync(InngestConnectionState lastObservedState, CancellationToken)`, which completes
with the state the connection moves to. `InngestConnectionState` is `Connecting`, `Active`, `Reconnecting`, `Closing`
or `Closed`.

`IHealthChecksBuilder.AddInngestConnect(string name = "inngest-connect", HealthStatus? failureStatus = null,
IEnumerable<string>? tags = null)`, in `Microsoft.Extensions.DependencyInjection`, adds a health check that is healthy
only while the connection is `Active`. See [Deploying](/inngest-dotnet/guides/deploying/).

## Aspire

Package `Inngest.Aspire.Hosting`, for the AppHost project. The resource type is in `Aspire.Hosting.ApplicationModel` and
the extension methods, on `IDistributedApplicationBuilder` and `IResourceBuilder<T>`, are in `Aspire.Hosting`, the
namespaces an AppHost imports. See [Aspire](/inngest-dotnet/guides/aspire/).

| Member | Purpose |
|---|---|
