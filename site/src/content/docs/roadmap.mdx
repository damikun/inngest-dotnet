The SDK covers what most workflows need: steps, sleeps, waits for events, parallel steps and fan-out, invocations,
flow control, retries, middleware, realtime, request signing with key rotation, and Connect workers, on .NET 8 and
.NET 10 and under Native AOT. The packages are on [NuGet](https://www.nuget.org/packages/Inngest).

## New in 1.3.0

New features, all compatible with code built against 1.2.0, then the fixes and the changes in behaviour.

- **The rest of the management API.** `IInngestManagementClient` covers apps, functions, one run, rerun, replay,
  invoke, traces, scores, experiments, Insights, environments, webhooks and sessions, on the v2 REST API that Inngest
  marks Beta. 1.2.0 paused and resumed functions, cancelled runs in bulk, and listed events, runs and syncs. See
  [Management](/inngest-dotnet/reference/api/#management).
- **Aspire, when the app is published.** A published app can reference the dev server and one self-hosted server.
  The dev server writes nothing into the manifest, so that reference does not replace the self-hosted settings. Two
  servers still throw while the AppHost runs, and two self-hosted servers throw in a manifest. See
  [Aspire](/inngest-dotnet/guides/aspire/).

### Fixes

- **Pooled buffers.** A buffer rented for a request or a response is cleared before it returns to the pool, so a
  later renter cannot read an event or a step.
- **Management lists.** A page whose cursor is the cursor just sent stops the list. The client throws
  `InngestException` instead of reading that page again.
- **Native AOT samples.** The samples set `RuntimeFrameworkVersion` to 10.0.15. SDK 10.0.401 would otherwise restore
  the Native AOT packs at 10.0.12, which NuGet audit rejects. See
  [Native AOT](/inngest-dotnet/guides/native-aot/).

### Changes in behaviour

- **The serve endpoint's body.** It follows the host's maximum request body size. When the host sets none, a body
  over 8 MiB is answered 413. The bytes read decide, not the declared `Content-Length`. Kestrel's own limit, 30 MB
  unless the app changes it, still applies when the host reports one. Inngest keeps a function call at or under 4 MB
  and the SDK loads anything larger itself.

## New in 1.2.0

New features, all compatible with code built against 1.1.0, then the fixes and the changes in behaviour.

- **Analyzers for replay safety and options.** INNGEST026 to INNGEST033 report code outside steps that reads the clock,
  a GUID or a random number, delays instead of sleeping, or uses a step id twice. They also report cron schedules,
  time strings and event triggers that the SDK or Inngest would refuse. Code fixes move a value into a step and turn a
  delay into a sleep. See [Check steps for replay safety](/inngest-dotnet/guides/source-generator/#check-steps-for-replay-safety)
  and [Check function options](/inngest-dotnet/guides/source-generator/#check-function-options).
- **Cron schedules checked at startup**, with the same rules Inngest uses to parse them.
- **A log scope for every call and step.** Logs written by services that a step calls carry the function, the run, the
  attempt and the step. `InngestOptions.LogScopes` turns it off. See [Logging](/inngest-dotnet/guides/functions-and-triggers/#logging).
- **The run's page.** In dev mode, `FunctionContext.RunUrl` links to the run in the dev server's UI.
- **The app instance in checkpoint requests.** Checkpoint requests send `X-Inngest-Instance-Id`, which is the Connect
  worker's id or `INNGEST_CONNECT_INSTANCE_ID`. See [Connect settings](/inngest-dotnet/guides/configuration/#connect-settings).
- **Waiting for runs.** `IInngestRunsClient.WaitForRunAsync`, `WaitForEventRunsAsync` and
  `WaitForEventRunsToSettleAsync` return runs once they have ended. In tests, `SendAndWaitAsync` on the test containers
  sends an event and returns the runs it started. See [Runs](/inngest-dotnet/reference/api/#runs) and
  [Sending an event and waiting for its runs](/inngest-dotnet/guides/testing-with-containers/#sending-an-event-and-waiting-for-its-runs).
- **A management client.** `IInngestManagementClient` uses Inngest's v2 REST API, which Inngest marks Beta, to pause
  and resume functions, cancel runs in bulk, and list events, runs and app syncs. See
  [Management](/inngest-dotnet/reference/api/#management).
- **Microsoft Agent Framework.** A guide and a sample for agents that make their model and tool calls as steps and wait
  for approval. See [Agent Framework](/inngest-dotnet/guides/agent-framework/).
- **Migration guides** from Durable Functions, Hangfire, MassTransit, Temporal and AWS Lambda durable functions.
- **The event version of an invoke.** `InvokeOptions.Version` sends the `v` of the event that starts the invoked run.

### Fixes

- **JSON as Inngest stores it.** Inngest sorts the keys of what it stores and reads numbers as doubles. So:
  - A type discriminator that comes back after the other properties is read. The `net10.0` build reads it anywhere in
    the object; the `net8.0` build, which .NET 8 and .NET 9 apps get, moves it to the front first. See
    [Serialization](/inngest-dotnet/guides/configuration/#serialization).
  - A checkpointed step hands the function its result as Inngest sends it on replay, so a step id made from the
    result stays the same.
  - A step result or invoke payload with a number that a double cannot hold, such as a `long` past 2^53, logs a
    warning. See [Numbers](/inngest-dotnet/guides/steps/#numbers).
- **Inngest's 4 MiB limit.** A step result is measured as Inngest measures it, in its data object and with the
  characters Go escapes, so one just under the limit fails with the SDK's clear error instead of a refused answer. A
  step error that Inngest would refuse for its size has its texts cut short, so the step is retried as usual instead
  of the run failing.
- **The SDK's HttpClient.** Resilience handlers that an app adds to every HttpClient, as Aspire's service defaults do,
  stay off the SDK's client. See [The SDK's HttpClient](/inngest-dotnet/guides/configuration/#the-sdks-httpclient).
- **Realtime:**
  - A streamed publish is no longer cut off by the HttpClient's 100 second timeout, and is never retried with half its
    text.
  - The text of a stream goes out in pieces gathered over 100 ms, so Inngest relays more of it.
  - A stream longer than the 1,000 pieces Inngest relays ends its request there with a warning, and the publish still
    returns all the text. Before, a long stream could fail with a broken connection.
  - A subscription's idle timeout is paused while the consumer handles a message.
- **Sending events.** When Inngest refuses part of a send, `SendEventsException` carries the ids of the events it
  accepted.
- **Settings.** Every Inngest setting is checked when the host starts, not only the app id.
- **Durable endpoints** (experimental):
  - A run is handed to Inngest one step to a call, and each call stays under the 4 MiB Inngest reads.
  - A run that finishes is recorded after the response, and the app waits for those records when it stops.
  - A hand-over that started finishes even if the client leaves.
  - The first hand-overs of a new endpoint wait until Inngest has stored it. Inngest stores a new endpoint in the
    background, and steps added to its first run before that were lost.
  - The run gets the signed-in user of the request that starts it. When taking the user fails, the run goes on
    without one.
- **Cancelled calls.** The tasks a cancelled call stops waiting for are observed, so their later failures are not
  reported as unobserved.
- **Blocked threads.** The SDK logs an error when function code blocks its thread while work for it waits, which would
  otherwise hang the call. INNGEST023 reports `.Result`, `.Wait()`, `GetAwaiter().GetResult()`, `Task.WaitAll` and
  `Task.WaitAny` on any task the function starts, not only on steps, and no longer reports a task that was awaited
  through `Task.WhenAll` of a collection.
- **Syncs.** A sync that Inngest refuses is answered with 400 and Inngest's reason, the only status whose reason
  Inngest shows. A trigger on `inngest/function.invoked` is left out of the sync, as in the TypeScript SDK, so the
  function no longer runs on every invoke of any function, and INNGEST033 counts it as no trigger.
- **Traces.** A call continues Inngest's trace when the host starts no span for the request, as on AWS Lambda, and links
  to a host span of another trace.
- **Connect.** A call whose answer is over the 8 MiB the gateway takes fails, instead of closing the connection. A
  worker keeps sending replies that Inngest did not take until it takes them or the worker stops.
- **Sentry and extended traces** flush after a call only, so an event sent outside a run does not wait for them.

### Changes in behaviour

- **Realtime:**
  - Text published to a topic goes as a JSON string, so text that reads as JSON, such as `42` or a model's JSON
    answer, reaches subscribers as text. It used to arrive as the number or object it reads as, which is what the
    TypeScript SDK still does. To publish JSON as an object, publish a `JsonElement` or a type.
  - `PublishAsync` throws `ArgumentException` for a message over the 512 KB Inngest reads, and a publish step with one
    fails without retries. Inngest used to cut such a message off.
- **Cancelled calls** wait up to 30 seconds for a step, a hook or the function's own code that ignores the token, and
  keep their services until it ends. Code that ignores the token makes app shutdown, and a cancelled run in the test
  host, take that long.
- **The test host** sends events and step results as Inngest does, with sorted keys and numbers read as doubles, so a
  test that checks a `long` past 2^53 or a decimal's trailing zeros after a step sees what production sees.
- **HttpClient handlers.** What a handler of the SDK's HttpClient throws, other than `HttpRequestException` and
  cancellation, is retried like a network failure and then arrives as `InngestException`.
- **Durable endpoints:**
  - Code outside steps sees the signed-in user only until the run's first wait. Read the user in a step before it.
  - After the app starts, and after a sync that Inngest takes as a change, the first request of each endpoint that hands
    its run over after a step, or records it in more than one call, waits up to a second.
  - While more than 100 runs wait to be recorded, a connection takes its next request only once its own run is
    recorded.
- **Syncs:** a sync that Inngest refuses with a 4xx is answered 400 instead of 500.
- **New log events.**
  - Warnings: 110 and 111 for a step or function code still running 30 seconds after its call was cancelled, 153 and
    156 for a durable endpoint run that a shutdown kept from being recorded, 155 for a durable endpoint user that
    could not be taken, 172 and 173 for numbers Inngest does not keep as written, and 354 for a stream longer than
    Inngest relays.
  - Errors: 112 for a function that holds its thread while work for it waits, 154 for a durable endpoint hand-over that
    failed after Inngest created the run, 527 for a Connect reply over 8 MiB, and 528 for Connect replies that keep
    failing to send.
  - Debug: 113, 174 and 175.
  - 524 is logged only when a stopping Connect worker gives up on its replies; before, it was logged after five
    failed rounds, and the replies waited for the next connection. `Inngest.Extensions.AI` logs 354 from the core in
    place of 824.
  - INNGEST023 reports more code. A project that treats warnings as errors fails to build on what it finds until the
    code is fixed or the warning suppressed.

## New in 1.1.0

New features, all compatible with code built against 1.0.0, and the changes in behaviour listed at the end.

- **Typed models for inference steps.** `AIModels` has OpenAI, OpenAI Responses, Anthropic, Gemini, Grok, DeepSeek and
  Azure OpenAI, each with typed requests and responses for `InferAsync`. See
  [Models of the providers](/inngest-dotnet/guides/steps/#models-of-the-providers).
- **What a model call used.** A step whose handler calls a model shows in the Inngest UI the models, the tokens, the
  settings and the time of the calls, without prompts or answers. See
  [What a model call used](/inngest-dotnet/guides/steps/#what-a-model-call-used).
- **Error codes.** An exception that implements `IHasErrorCode`, or has a `"code"` entry in its `Data`, keeps its code
  in what Inngest records and in the `StepFailedException` of a failed step. See
  [Recover from a failed step](/inngest-dotnet/guides/errors-and-retries/#recover-from-a-failed-step).
- **Cancel handlers.** `ICancelHandler`, or `onCancel` next to `onFailure`, runs code after a run was cancelled. See
  [Run code when a run is cancelled](/inngest-dotnet/guides/errors-and-retries/#run-code-when-a-run-is-cancelled).
- **Step input transforms.** `IPayloadTransform.TransformStepInput` rewrites what a step was made with. See
  [What is encrypted](/inngest-dotnet/guides/middleware/#what-is-encrypted).
- **Stable ids for the events a step sends.** An event sent without an `Id` gets one made of the run, the step and its
  place in the list, so a step that runs again starts no second runs. See
  [From a function](/inngest-dotnet/guides/sending-events/#from-a-function).
- **Inngest's limits, checked in the app.** A step result over 4 MiB fails the step without retries, a send of more than
  5,000 events throws, and a warning says when a run passes 1,000 steps or 32 MiB of state.
- **Other hosts.** `InngestCommHandler` is public, so any HTTP host can serve functions, and `InngestSignatureVerifier`
  checks Inngest's signature in app code. See [On another host](/inngest-dotnet/guides/deploying/#on-another-host).
- **Realtime with a token from elsewhere.** `IInngestRealtime.SubscribeAsync(RealtimeToken)` receives the messages a
  token minted by another app allows. See
  [With a token from elsewhere](/inngest-dotnet/guides/realtime/#with-a-token-from-elsewhere).
- **More in the test host.** Mocks for send-event steps and for sends and publishes that fail, and `RunUntilAsync`,
  which stops a run at a checkpoint. See [Mocking steps](/inngest-dotnet/guides/testing/#mocking-steps).
- **Durable endpoint output on the app's domain.** `MapInngestDurableEndpointProxy` serves a run's output with CORS
  headers, and decrypts it when the encryption middleware encrypted it. See
  [The output on the app's own domain](/inngest-dotnet/guides/durable-endpoints/#the-output-on-the-apps-own-domain).
- **Analyzers for replay safety.** `INNGEST020` to `INNGEST025` find step code that breaks when a run replays, such as
  state set inside a step and read outside it, step ids made from the clock and steps blocked on with `.Result`, with
  a code fix that awaits the step. See
  [Check steps for replay safety](/inngest-dotnet/guides/source-generator/#check-steps-for-replay-safety).
- **Extended traces** (experimental, `INNGESTEXP002`). `AddExtendedTraces()` sends the spans the app's code makes while
  a function runs to Inngest, which shows them in the run's trace. See
  [Extended traces](/inngest-dotnet/reference/api/#extended-traces).
- **Sentry performance.** `Inngest.Sentry` reports every call as a transaction with a span for each step. See
  [Spans](/inngest-dotnet/guides/middleware/#spans).
- **Inngest v1.52.0.** The tests run against `inngest/inngest:v1.52.0`, the Aspire integration runs that tag, and
  `dotnet inngest dev` downloads that version.

### Changes in behaviour

- **Durable endpoints** (experimental):
  - Their API is marked `INNGESTEXP001` instead of `INNGEST001`, so change the `NoWarn` that suppresses it.
  - Outside dev mode, an app with durable endpoints does not start without `ServeOrigin`, or `INNGEST_SERVE_ORIGIN`.
    Inngest resumes a run at the origin its event records and signs the original body for it, and the origin of the
    request comes from its `Host` header, which the client chooses. See
    [Configuration](/inngest-dotnet/guides/durable-endpoints/#configuration).
  - With the encryption middleware, the output of a run that finishes in its first request is encrypted, as a resumed
    run's already was.
- **Encryption:**
  - The data of invokes is encrypted, so the invoked function needs the encryption middleware as well, as it does for
    events. The TypeScript package reads it.
  - The steps of `Inngest.Extensions.AI` record no input while encryption runs for the function, because Inngest stores
    the input of a step in the clear.
- **User context:** an event that the middleware writes no user for loses the reserved `_inngest_dotnet_user` key, so
  that a protected user copied from someone else's event is never sent on.
- **New warnings:**
  - The step analyzers run in every project that references `Inngest`. A project that treats warnings as errors fails
    to build on what they find until it is fixed or suppressed.
  - A sync that registers an `http://` URL for a request that came through a proxy over https logs a warning, event id
    417. See [Behind a proxy](/inngest-dotnet/guides/configuration/#behind-a-proxy).
- **Sentry:** with `TracesSampleRate` or `TracesSampler` set, the calls of functions are sampled and sent as
  transactions like any other.

## New in 1.0.1

Bug fixes, with no change to the public API:

- A step's handler runs in the execution context of the code that called the step, so an `AsyncLocal`, the current
  `Activity` or a logging scope set around the call is there in the handler too.
- A fetch step claims its id when it is called, and a parallel group with a fetch whose body is still being read is
  reported to Inngest as one group.
- An invoke step fails when the invoked run was cancelled, instead of returning the run's finished event as its output.
- A `NonRetriableException` thrown by an event transform or the event type fails the run without retries.
- The error for a stored step result that cannot be read names the step and the type.
- A Connect worker keeps the newest lease of a request when Inngest renews it while an extension is on its way.
- `Inngest.Extensions.AI`: model calls after a tool call no longer log the warning about reused step ids, and a replay
  of a conversation no longer warns that a result was made for another input.
- New samples of an AI agent that streams its work to a page and of one that waits for a person to approve its
  actions, and corrections across the docs.

## New in 1.0.0

1.0.0 brings every package to its first major version, and adds 16 packages to the 5 that 0.1.0 had. From here on,
each package is checked against 1.0.0, so a change that would break code built against it fails the build. Durable
endpoints are the exception: they stay marked experimental and may still change.

- **A health check for apps that serve functions.** `AddInngest` on the health checks builder tells a readiness probe
  whether the app has its keys and Inngest answers a request that carries the signing key. It keeps the answer for 30
  seconds, and with `CheckSync` it also asks Inngest whether the app is synced. See
  [Health checks](/inngest-dotnet/guides/deploying/#health-checks).
- **AI calls as steps.** `AIWrapAsync` runs your own model call as a step that the Inngest UI shows with its input,
  and a rerun with an input edited there hands the handler the edited one. An input edited for `InferAsync` now
  reaches the request too.
- **Realtime.** Steps publish messages and stream text, such as a model's reply, once each; typed topics check what is
  published; `IInngestRealtime` publishes from anywhere, receives messages in .NET as an `IAsyncEnumerable` and mints
  tokens for the TypeScript SDK's `useRealtime`; and `MapInngestRealtime` relays messages to browsers as server-sent
  events, one subscription to Inngest for all the pages that watch a channel. See
  [Realtime](/inngest-dotnet/guides/realtime/).
- **Streaming.** `InngestOptions.Streaming`, or `INNGEST_STREAMING=true`, keeps a long call open behind proxies and
  load balancers that close idle connections. See [Behind a proxy](/inngest-dotnet/guides/configuration/#behind-a-proxy).
- **Sessions.** Events carry the sessions they belong to, a run's sessions are in `context.Sessions`, and what the run
  sends or invokes inherits them. See [Sessions](/inngest-dotnet/guides/sending-events/#sessions).
- **A test host for every step.** Mocks for waits for signals, sent signals, fetch and inference steps; AI wrap steps
  take run mocks; signals and realtime messages are recorded like events.
- **An Aspire integration.** `Inngest.Aspire.Hosting` runs the Inngest dev server, or a self-hosted server that signs its
  requests, as a container of an Aspire AppHost. It links the server's UI in the dashboard, syncs the apps of the
  AppHost and gives projects, containers and Connect workers the settings they need. See
  [Aspire](/inngest-dotnet/guides/aspire/).
- **A scope per step.** `RunScopedAsync` runs a step in a dependency injection scope of its own, created when the
  handler starts and disposed when it ends, so a `DbContext` is new for every step and attempt and nothing it tracks
  reaches the next one. The guide covers one `SaveChangesAsync` per step, transactions and execution strategies, and
  idempotency keys for steps that can run again. See [Scoped steps](/inngest-dotnet/guides/scoped-steps/).
- **Sentry and encryption packages.** `Inngest.Sentry` reports the errors of functions and steps to Sentry, tagged
  with the app, the function, the run and the event. `Inngest.Encryption` encrypts event data, step results and
  function output in the format of the TypeScript SDK's encryption middleware, so .NET and TypeScript services read
  each other's data. See [Middleware](/inngest-dotnet/guides/middleware/#encryption).
- **Durable endpoints.** An ASP.NET Core endpoint whose handler runs steps like a function. The caller gets the
  response directly, and Inngest takes the run over only when a step has to wait or fails. `UseInngestDurableEndpoints`
  and `WithDurableEndpoint`, or `[DurableEndpoint]` on a controller, set it up. Inngest calls the feature beta, so the
  .NET API is marked experimental and may change. See [Durable endpoints](/inngest-dotnet/guides/durable-endpoints/).
- **Tests against a real Inngest server.** `Inngest.Testing.Containers` is a Testcontainers module that runs the dev
  server, or a self-hosted server with signing and event keys, in Docker from your tests, points an app at it and has
  it sync the app, with the Connect gateway if you want one. `Inngest.Testing.Containers.AspNetCore` runs an ASP.NET Core
  app under `WebApplicationFactory` on a real port for it, on .NET 10. See
  [Testing with containers](/inngest-dotnet/guides/testing-with-containers/).
- **Chat clients as steps.** `Inngest.Extensions.AI` makes the model calls and the tool calls of a Microsoft.Extensions.AI
  `IChatClient` steps of the run, so a replay or a retry of a later step never calls the model or a tool twice. See
  [AI chat clients](/inngest-dotnet/guides/ai/).
- **A transactional outbox.** `Inngest.EntityFrameworkCore` saves events in the same Entity Framework Core transaction as
  your data, and a hosted dispatcher sends them afterwards, each under the id it got when it was added. See
  [Transactional outbox](/inngest-dotnet/guides/outbox/).
- **A source generator and analyzers.** A project that sets `InngestGenerateFunctionRegistration` gets
  `AddInngestFunctions()`, which registers its function classes without reflection, and an analyzer reports the types a
  Native AOT app has not listed in its `JsonSerializerContext`, with a code fix that adds them. Both come with the
  `Inngest` package. See [Source generator and analyzers](/inngest-dotnet/guides/source-generator/).
- **Templates and a dev server command.** `dotnet new inngest-web` and `dotnet new inngest-worker`, from the
  `Inngest.Templates` package, make a project with a typed event, a function and dev mode in its Development settings.
  `dotnet inngest dev`, from the `dotnet-inngest` tool, downloads the Inngest CLI, checks its SHA-256 and runs the dev
  server for the app, whose address it reads from the launch settings. See
  [Templates and tool](/inngest-dotnet/guides/templates-and-tools/).
- **Fan-out over a list.** `MapAsync` runs a step for each item of a list, with a limit on how many run at once, and
  returns the results in the order of the items. `ForEachAsync` does the same without results, `MapOutcomesAsync` runs
  every item and gives each its outcome, and `MapInChunksAsync` hands a list too long for one run to child runs in
  chunks. See [Fan-out over a list](/inngest-dotnet/guides/fan-out/).
- **Webhooks.** `Inngest.Webhooks` verifies the signatures of webhooks from Stripe, GitHub, Shopify, Standard Webhooks
  senders such as Clerk and Resend, and any HMAC. `MapInngestWebhook` sends each delivery as an event whose id is the
  delivery id, so a redelivery within 24 hours starts no second run. See [Webhooks](/inngest-dotnet/guides/webhooks/).
- **The user behind a run.** `Inngest.UserContext` carries selected claims of the signed-in user who sent an event into
  the runs it starts, protected with ASP.NET Core Data Protection, and a function reads them as `ICurrentUser` or
  `ClaimsPrincipal`. `Inngest.UserContext.AspNetCore` takes the user from `HttpContext.User`. See
  [User context](/inngest-dotnet/guides/user-context/).
- **AWS Lambda and Azure Functions.** `Inngest.AwsLambda` serves functions from a Lambda function behind API Gateway or
  a function URL with `InngestLambdaHandler`, also as a Native AOT executable. `Inngest.AzureFunctions` serves them
  from an HTTP-triggered function of the isolated worker with `ServeInngestAsync`. See
  [Running on AWS Lambda](/inngest-dotnet/guides/aws-lambda/) and
  [Azure Functions](/inngest-dotnet/guides/azure-functions/).
- **Realtime in Blazor and SignalR.** `Inngest.Blazor` shows realtime messages with `RealtimeView<TData>` in Blazor
  Server, WebAssembly and interactive Auto. `Inngest.SignalR` forwards them to the clients of a SignalR hub, with one
  subscription to Inngest shared by the clients of a channel. See [Realtime in Blazor](/inngest-dotnet/guides/blazor/)
  and [SignalR](/inngest-dotnet/guides/signalr/).
- **Docs for AI assistants.** Every page of this site has a Markdown copy, `llms.txt` lists them and `llms-full.txt`
  holds them all, so a coding assistant can read the docs as text. A guide lists the names that differ from the
  TypeScript SDK and the rules that keep a function correct when it replays. See
  [AI coding assistants](/inngest-dotnet/guides/ai-assistants/).

## New in 0.1.0

The first stable release of `Inngest`, `Inngest.AspNetCore`, `Inngest.Connect`, `Inngest.Testing` and
`Inngest.OpenTelemetry`, with the fixes of a second code review:

- Middleware that finishes async work after the call has answered no longer makes the SDK spin on the thread pool, and
  hooks can wait on the tasks a function started, as step handlers can.
- `off` and `no` in Inngest's environment variables, such as `INNGEST_DEV=off`, read as false.
- A call that finished answers even when disposing its services throws.
- Checkpointed steps and runs with deeply nested outputs read back.
- Batch timeouts are written in hours, which Inngest can parse.
- A Connect worker's instance id defaults to the full host name, as in the TypeScript SDK.

## New in 0.1.0-preview.3

- **Fixes from a code review.** A step that awaits a task the function started before it no longer hangs the call,
  and a task the function started, such as one a singleton caches, completes even after the call has answered.
  Connect keeps flushing replies over HTTP whatever the HTTP client throws, and no longer gives up a lease Inngest
  has just renewed. Deeply nested step results read back, and the endpoint gets past an app's fallback
  authorization policy.
- **Safer defaults.** The event key stays out of the HttpClient logs, an address without a scheme gets `https`
  outside a private network, and an unsigned sync that takes its URL from the request logs a warning.
- **Every configuration problem at once.** The SDK checks every function at startup and lists all problems, each
  naming its function. It also refuses duplicate triggers, as Inngest does, and accepts a concurrency limit of 0,
  which means no limit.
- **Attributes of your own.** The trigger and flow control attributes derive from `FunctionOptionsAttribute`, so an
  app can write an attribute that bundles options several functions share.
- **Every step type in telemetry**, with names for signal, fetch and AI steps too.
- **A test host closer to Inngest.** A function's own middleware runs around mocked steps and recorded sends, the
  ids of one send sort in send order, and calls carry a job id.
- **Checked packages.** Each package is validated against the previous release, so a breaking API change fails the
  build, and the packages depend on exactly the Inngest of their own version.

## New in 0.1.0-preview.2

- **Typed events.** An event's data record implements `IInngestEventData` and carries the event's name, so sends,
  triggers, waits and cancellations name the type instead of repeating a string.
- **Attributes on function classes.** `[InngestFunction]`, `[EventTrigger<T>]`, `[CronTrigger]`, `[Concurrency]`,
  `[CancelOn<T>]` and the other flow control attributes keep a function's id, triggers and limits on its class.
  `AddFunction<T>()` reads them, and options written in code work as before.
- **Typed results and invoke by class.** `InngestFunction<TEvent, TResult>` gives a function a result type, and
  `InvokeAsync<TFunction, TResult>` invokes it by its class, with the compiler checking the result.
- **Settings from `appsettings.json`.** `AddInngest(builder.Configuration.GetSection("Inngest"))` reads the
  `Inngest` section, and `INNGEST_*` variables still win over it. Like the attributes and typed events, it works
  under Native AOT.
- **The test host by class.** `RunAsync<TFunction>` runs a function by its class, and
  `StepMocks.Invoke<TFunction, TResult>` checks what a mocked invoke returns.

## New in 0.1.0-preview.1

- **A test host, `Inngest.Testing`.** Unit-test a function the way Inngest runs it, call by call, with mocks for
  steps, sleeps, waits and invokes.
- **OpenTelemetry, `Inngest.OpenTelemetry`.** Traces for calls and steps, and metrics for runs, retries and
  durations, without writing the middleware yourself.
- **Connect health checks.** The worker's connection state and a health check for readiness probes.
- **Race mode for parallel steps.** A race resumes as soon as its first step finishes, for races such as approved
  or rejected.
- **A runs client.** Read a run's status and output, list the runs of an event, and cancel runs from your own code.
- **Signals, durable fetch and AI inference** as steps, and sending events or signals to another environment.
- **Checkpointing, opt-in.** Consecutive steps run in one request and are saved to Inngest in the background, with
  fewer requests per run.
- **Smaller additions.** Event access in middleware, middleware for one function, payload transforms, typed system
  events, the cause of a failed step, cron jitter and readable step names in the Inngest UI.
