With [Connect](https://www.inngest.com/docs/durable-execution/deploying-functions/connect), the app opens a
WebSocket to Inngest and receives work over it, instead of exposing an HTTP endpoint for Inngest to call. That suits
workers behind a firewall or a NAT, apps without a public URL, and long-running processes such as a container that
should not also be a web server.

The functions are the same. Only the way they are served changes.

## Set up a worker

Install `Inngest.Connect` from NuGet. It brings in `Inngest`:

```bash
dotnet add package Inngest.Connect
```

Or reference it in the project file. `*` restores the newest version; put a version such as
`1.0.0` there instead to pin it:

```xml title="Worker.csproj"
<ItemGroup>
  <PackageReference Include="Inngest.Connect" Version="*" />
</ItemGroup>
```

Then call `AddConnect` instead of mapping an endpoint. A worker needs no web server at all; the generic host is
enough:

```csharp title="Program.cs"
using Inngest;

var builder = Host.CreateApplicationBuilder(args);

builder.Services.AddSingleton<IEmailSender, SmtpEmailSender>();
builder.Services
    .AddInngest(options => options.AppId = "shop-worker")
    .AddFunction<OnboardUser>()
    .AddConnect(connect =>
    {
        connect.InstanceId = Environment.GetEnvironmentVariable("HOSTNAME");
        connect.MaxWorkerConcurrency = 20;
    });

await builder.Build().RunAsync();
```

Functions are defined and registered the same way for a worker as for an endpoint, with their options as attributes
on the class or [in code](/inngest-dotnet/guides/functions-and-triggers/#code-first-or-attributes).
`AddConnect` registers a hosted service. It connects when the host starts and syncs the app through the
connection, so there is no URL to sync and nothing to call `PUT` on. An ASP.NET Core app can use `AddConnect` too, alongside
its own endpoints; it then needs no `MapInngest`.

## Options

| Option | Variable | Meaning |
|---|---|---|
| `InstanceId` | | Identifies this worker to Inngest, which tracks leases and capacity per instance. Keep it stable across restarts of one worker and unique between workers. Defaults to the host name, as in the TypeScript SDK; workers that share a host, such as several processes, need an id each. |
| `MaxWorkerConcurrency` | `INNGEST_CONNECT_MAX_WORKER_CONCURRENCY` | The most executions Inngest sends to this worker at once. Unlimited by default. |
| `GatewayUrl` | `INNGEST_CONNECT_GATEWAY_URL` | A `ws://` or `wss://` URL to dial instead of the gateway Inngest assigns, for when a proxy or port mapping sits in between. |

The app id, keys, environment and Inngest's address come from `InngestOptions` as usual; see
[Configuration](/inngest-dotnet/guides/configuration/). In cloud mode the worker needs a signing key and refuses to
start without one.

## Run it locally

The dev server runs a Connect gateway on port 8289. Publish that port as well as 8288, and start the worker in dev
mode:

<DevServer connect />

```bash
INNGEST_DEV=1 dotnet run
```

The app appears in the dev server's Apps page as soon as the worker connects. `--no-discovery` stops the dev
server from looking for HTTP apps, which a worker does not have.

In an Aspire AppHost, [`AddInngest`](/inngest-dotnet/guides/aspire/) runs the dev server for you, and `WithReference`
gives the worker the address of the gateway, which Aspire publishes on a port of its own.

## What the worker does

Once connected, the worker:

- receives each call as a message, acknowledges it and runs it through the same execution engine as an HTTP call,
  so functions behave the same either way;
- extends the call's lease while it runs, so Inngest does not hand it to another worker;
- sends heartbeats, and reconnects with backoff, from one second up to five minutes, when the connection drops;
- opens a new connection before closing the old one when Inngest drains a gateway;
- switches to the fallback signing key when Inngest refuses the current one.

A slow function never holds up heartbeats or lease extensions: the socket has its own reader and writer, and
functions run on the thread pool.

## Shutting down

When the host stops, the worker tells Inngest to send it no more work, waits for running calls to finish, and closes
the connection. Calls still running when the host's shutdown timeout passes are cancelled through their
`CancellationToken`, and Inngest retries them elsewhere. Give the host enough time for your longest step:

{/* check: statements; HostApplicationBuilder builder */}
```csharp
builder.Services.Configure<HostOptions>(options => options.ShutdownTimeout = TimeSpan.FromMinutes(2));
```

On platforms that stop containers with `SIGTERM`, such as Kubernetes or ECS, set the platform's grace period a
little longer than that timeout.
