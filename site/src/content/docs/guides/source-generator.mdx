The `Inngest` package carries a source generator, two analyzers and a code fix. The compiler loads them from the
package, so there is nothing more to install: every project that references `Inngest`, directly or through
`Inngest.AspNetCore` or `Inngest.Connect`, has them. They are built against Roslyn 4.8, the compiler of the .NET 8 SDK
and Visual Studio 17.8, and run in that compiler and in every newer one.

- The generator writes `AddInngestFunctions()`, which registers the function classes of the project.
- One analyzer says why a class with `[InngestFunction]` is not registered.
- The other one, in an app that turns reflection-based JSON off, finds the types that no `JsonSerializerContext`
  lists. A code fix lists them.

## Register the function classes

Give each function class `[InngestFunction]`, and register all of them with one call:

{/* check: file isolated */}
```csharp title="Functions.cs"
using Inngest;

public sealed record OrderPlaced(string OrderId) : IInngestEventData
{
    public static string EventName => "shop/order.placed";
}

[InngestFunction("charge-order", Retries = 3)]
[EventTrigger<OrderPlaced>]
public sealed class ChargeOrder : InngestFunction<OrderPlaced>
{
    public override async Task<object?> ExecuteAsync(FunctionContext<OrderPlaced> context, CancellationToken cancellationToken)
    {
        await context.Step.RunAsync("charge", () => context.Logger.LogInformation("Charging {OrderId}", context.Event.Data.OrderId));
        return null;
    }
}

[InngestFunction("send-receipt")]
[EventTrigger<OrderPlaced>]
public sealed class SendReceipt : InngestFunction<OrderPlaced>
{
    public override Task<object?> ExecuteAsync(FunctionContext<OrderPlaced> context, CancellationToken cancellationToken) =>
        Task.FromResult<object?>(null);
}
```

```csharp title="Program.cs"
using Inngest;

var builder = WebApplication.CreateBuilder(args);

builder.Services
    .AddInngest(options => options.AppId = "shop")
    .AddInngestFunctions();

var app = builder.Build();
app.MapInngest();
app.Run();
```

`AddInngestFunctions()` is the same as writing `AddFunction<ChargeOrder>()` and `AddFunction<SendReceipt>()`, for every
class. The compiler finds the classes while it builds the project, from the attribute, so there is no assembly scanning
at run time and nothing for the trimmer to keep. What the generator writes for the project above:

{/* check: skip */}
```csharp
namespace Inngest
{
    internal static class InngestFunctionRegistration_Shop
    {
        internal static global::Inngest.IInngestBuilder AddInngestFunctions(this global::Inngest.IInngestBuilder builder)
        {
            global::System.ArgumentNullException.ThrowIfNull(builder);

            global::Inngest.InngestBuilderExtensions.AddFunction<global::ChargeOrder>(builder);
            global::Inngest.InngestBuilderExtensions.AddFunction<global::SendReceipt>(builder);

            return builder;
        }
    }
}
```

The order of the calls is the order of the classes' names, so adding a file never reorders them. The method is in the
`Inngest` namespace, with `AddFunction`, and it returns the builder, so more registrations can follow it.

`AddFunction<T>()` still reads the attributes of each class when the app starts, as it does when you call it yourself.
The generator decides which classes to register, not what their options are.

### Classes it leaves out

The method registers a class that has `[InngestFunction]`, derives from `InngestFunction<TEventData>` or
`InngestFunction<TEventData, TResult>`, and that generated code in the same project can create and name. A class that
does not fit is left out, and the project builds with a diagnostic on it that says why:

| Diagnostic | The class |
|---|---|
| [`INNGEST001`](#inngest001), error | has the attribute but is not a function: it does not derive from `InngestFunction<TEventData>` or `InngestFunction<TEventData, TResult>`. |
| [`INNGEST002`](#inngest002) | is abstract. |
| [`INNGEST003`](#inngest003) | is generic, or inside a generic class. |
| [`INNGEST004`](#inngest004) | is private, protected or file-local, or inside a type that is. |
| [`INNGEST005`](#inngest005) | has no public constructor. |

Public and internal classes are registered, nested ones too, in any namespace or none. A class registered in code with
`FunctionOptions` needs no attribute, and so is not in the generated method.

### Several projects

Each project that references Inngest gets a method of its own, for its own classes. The method is `internal`, so a
library's method does not meet the app's, which has the same name. To register a library's functions in the app, give
the library a method name of its own and make it public:

```xml title="Shop.Billing.csproj"
<PropertyGroup>
  <InngestFunctionsMethodName>AddBillingFunctions</InngestFunctionsMethodName>
  <InngestFunctionsAccessibility>public</InngestFunctionsAccessibility>
</PropertyGroup>
```

{/* check: skip */}
```csharp title="Program.cs"
builder.Services
    .AddInngest(options => options.AppId = "shop")
    .AddInngestFunctions()
    .AddBillingFunctions();
```

Two public methods with the same name in the same namespace make the call ambiguous, and the compiler says so
(`CS0121`). A library that keeps the default internal method can instead register its functions in a public method of
its own: `public static IInngestBuilder AddBillingFunctions(this IInngestBuilder builder) => builder.AddInngestFunctions();`.

The MSBuild properties:

| Property | Default | Meaning |
|---|---|---|
| `InngestFunctionsMethodName` | `AddInngestFunctions` | The name of the generated method. It must be a C# identifier. |
| `InngestFunctionsAccessibility` | `internal` | `public` or `internal`, for the class and the method. |
| `DisableInngestSourceGenerator` | `false` | `true` takes the generator and the analyzers out of the build. |

A value the generator cannot use is reported as [`INNGEST006`](#inngest006), and the default is used.

### What it does not do

- It registers the classes of the project it compiles, not those of the projects it references. Each of those has its
  own method, or none.
- It leaves no class out on request. A class that has the attribute is registered by the method, and a second
  registration by hand fails when the app starts, because the function id is used twice. A function that needs
  `AddFunction<T>(configure)` is registered by hand, and so is every other function of the same app.
- It does not compute the options at compile time. They are read from the attributes when the app starts.

## Check the JSON of a Native AOT app

An app that is published with Native AOT or trimmed has no reflection-based JSON, so every type that Inngest reads or
writes for your functions must be listed by a source-generated `JsonSerializerContext`. A type that is not fails when
the function runs, with a `NotSupportedException`. The [Native AOT guide](/inngest-dotnet/guides/native-aot/) explains
the context. The analyzer finds the types that are missing while the project builds.

It runs when the project sets `PublishAot` or `PublishTrimmed` to `true`, or `JsonSerializerIsReflectionEnabledByDefault`
to `false`. A project that sets `JsonSerializerIsReflectionEnabledByDefault` to `true` is not checked. In any other
project the analyzer does nothing.

It looks at:

- the event data and the result type of every function class, that is, the `TEventData` and `TResult` of its base class;
- the event data type of a function registered with `AddFunction<TEventData>(options, handler)`;
- the result type of every `RunAsync<T>` step.

A type counts as listed when a context lists it with `[JsonSerializable]`, or when a type that a context lists has it
as a property, a field, a constructor parameter, a type argument or a derived type, because the generator of
`System.Text.Json` writes metadata for all of those. The context can be in the project or in a project it references.
Types that the SDK serializes with a context of its own, such as `JsonElement`, `object` and `FunctionFailure`, are
not asked for. An anonymous type cannot be listed at all, so it gets a message of its own.

{/* check: file isolated */}
```csharp title="Functions.cs"
using System.Text.Json.Serialization;
using Inngest;

public sealed record Refund(string OrderId);

public sealed record Receipt(string Id);

[InngestFunction("refund")]
public sealed class OnRefund : InngestFunction<Refund, Receipt>
{
    public override Task<Receipt> ExecuteAsync(FunctionContext<Refund> context, CancellationToken cancellationToken) =>
        Task.FromResult(new Receipt(context.Event.Data.OrderId));
}

[JsonSerializable(typeof(Refund))]
internal sealed partial class ShopJson : JsonSerializerContext;
```

With `PublishAot` on, the project above builds with a warning on `Receipt`:

```text
warning INNGEST010: 'Receipt' is the result of function 'OnRefund', but no JsonSerializerContext lists it with
[JsonSerializable], and reflection-based JSON is turned off
```

The code fix, in the IDE, adds `[JsonSerializable(typeof(Receipt))]` to a context of the project, and the `using`
directive the type needs if the file lacks it. It offers one fix for each context the project has. It does not fix all
the diagnostics of a project in one go, and it offers nothing when the project has no context: declare one first, as
the Native AOT guide shows.

### Why the generator does not list the types itself

The generator knows these types, so it could write the `[JsonSerializable]` attributes. It cannot: the generator of
`System.Text.Json` reads the attributes of your source, and a source generator's output is not input to another
generator. Code that Inngest's generator added to the context would not be seen. The code fix writes the attribute into
your own file instead.

### What the analyzer does not check

- Values of a type that is only known at run time, such as an `object` that holds a record.
- Events your code sends, and the types of `WaitForEventAsync`, `InvokeAsync`, `InferAsync` and the other steps. List
  those yourself, as the [Native AOT guide](/inngest-dotnet/guides/native-aot/#which-types-to-list) says.
- Contexts that are built in code, and options whose resolver chain does not contain the context. Test the paths that
  matter after you publish.

## Diagnostics

Every diagnostic has an id that `.editorconfig` can configure, such as `dotnet_diagnostic.INNGEST010.severity = none`,
and `#pragma warning disable` works on the class or the call the diagnostic is on.

### INNGEST001

Error. A class has `[InngestFunction]` but does not derive from `InngestFunction<TEventData>` or
`InngestFunction<TEventData, TResult>`. The attribute does nothing on any other class: the class cannot be registered,
by `AddFunction<T>()` or by the generated method, and Inngest never runs it. Add the base class, or remove the
attribute.

### INNGEST002

Warning. The class is abstract. The service provider cannot create it, and `[InngestFunction]` is not inherited, so the
classes that derive from it are not registered either. Put the attribute on each concrete class.

### INNGEST003

Warning. The class is generic, or inside a generic class. The generator does not know which type arguments the app
uses. Register the closed types with `AddFunction<T>()`, or suppress the warning on a class that is only a template.

### INNGEST004

Warning. The class, or a type that contains it, is private, protected or file-local. The generated method is outside
it. Make the class public or internal, with every type that contains it, or register it with `AddFunction<T>()` from
inside the containing type.

### INNGEST005

Warning. The class has no public constructor. The service provider calls public constructors only, so every call of the
function would fail. Add one.

### INNGEST006

Warning. `InngestFunctionsMethodName` is not a C# identifier, or `InngestFunctionsAccessibility` is neither `public`
nor `internal`. The generator uses the default.

### INNGEST010

Warning. A type that Inngest serializes for a function is missing from the `JsonSerializerContext`, in a project that
turns reflection-based JSON off. Add `[JsonSerializable(typeof(...))]` for it to a context, which the code fix does.

### INNGEST011

Warning. The type is anonymous, which no context can list. Use a record, a class or a struct, and list it.
