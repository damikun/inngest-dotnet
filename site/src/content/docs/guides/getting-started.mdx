In about five minutes you will have an ASP.NET Core app with a durable function running on your machine. When a
user signs up, it sends a welcome email, waits, and sends a second one; if the second email fails, a retry sends
only that one. The dev server shows every step as it happens.

<LocalSetup />

<Aside title="You need">

- The [.NET SDK](https://dotnet.microsoft.com/download), version 8 or 10.
- A way to run the [Inngest dev server](https://www.inngest.com/docs/local-development): its install script,
  Homebrew, Node.js or Docker.

</Aside>

## 1. Add the SDK

Install `Inngest.AspNetCore` from NuGet. It brings in `Inngest`. The version is a preview, so add `--prerelease`:

```bash
dotnet add package Inngest.AspNetCore --prerelease
```

Or reference it in the project file. `*-*` restores the newest version, previews included; put a version such as
`0.1.0-preview.3` there instead to pin it:

```xml title="Shop.csproj"
<ItemGroup>
  <PackageReference Include="Inngest.AspNetCore" Version="*-*" />
</ItemGroup>
```

The SDK is split into these packages:

| Package | What it gives you |

| [`Inngest.Testing`](https://www.nuget.org/packages/Inngest.Testing/) | An in-memory test host that runs your functions on the real execution engine. See [Testing functions](/inngest-dotnet/guides/testing/). |
| [`Inngest.Testing.Containers`](https://www.nuget.org/packages/Inngest.Testing.Containers/) | A Testcontainers module that runs the Inngest dev server or a self-hosted server in Docker for end-to-end tests. See [Testing with containers](/inngest-dotnet/guides/testing-with-containers/). |

## 2. Write a function

A function is a class. `[InngestFunction]` gives it an id and `[EventTrigger]` names the event that starts it. Each
`RunAsync` is a step: it runs once and Inngest saves its result. `SleepAsync` pauses the run without holding a thread.

```csharp title="OnboardUser.cs"
using Inngest;

public sealed record UserSignedUp(string UserId, string Email);

[InngestFunction("onboard-user")]
[EventTrigger("user/signed-up")]
public sealed class OnboardUser(IEmailSender email) : InngestFunction<UserSignedUp>
{
    public override async Task<object?> ExecuteAsync(FunctionContext<UserSignedUp> context, CancellationToken cancellationToken)
    {
        var user = context.Event.Data;

        await context.Step.RunAsync("send-welcome-email",
            ct => email.SendAsync(user.Email, "Welcome!", ct));

        await context.Step.SleepAsync("wait-before-tips", TimeSpan.FromSeconds(30));

        await context.Step.RunAsync("send-tips",
            ct => email.SendAsync(user.Email, "Three things to try first", ct));

        return new { user.UserId };
    }
}
```

The email service only logs for now:

```csharp title="EmailSender.cs"
public interface IEmailSender
{
    Task SendAsync(string to, string subject, CancellationToken cancellationToken);
}

public sealed class ConsoleEmailSender(ILogger<ConsoleEmailSender> logger) : IEmailSender
{
    public Task SendAsync(string to, string subject, CancellationToken cancellationToken)
    {
        logger.LogInformation("Sending \"{Subject}\" to {To}", subject, to);
        return Task.CompletedTask;
    }
}
```

## 3. Serve it

`AddInngest` registers the SDK and the function, `MapInngest` maps the endpoint Inngest calls, and `/signup`
sends the event that starts a run:

```csharp title="Program.cs"
using Inngest;

var builder = WebApplication.CreateBuilder(args);

builder.Services.AddSingleton<IEmailSender, ConsoleEmailSender>();
builder.Services
    .AddInngest(options => options.AppId = "shop")
    .AddFunction<OnboardUser>();

var app = builder.Build();

app.MapInngest("/api/inngest");

app.MapPost("/signup", async (SignupRequest request, IInngestClient inngest, CancellationToken cancellationToken) =>
{
    var userId = Guid.NewGuid().ToString("N");
    await inngest.SendAsync(new InngestEvent("user/signed-up", new UserSignedUp(userId, request.Email)), cancellationToken);
    return Results.Accepted(value: new { userId });
});

app.Run();

public sealed record SignupRequest(string Email);
```

The function's options are attributes on the class here. They can also be passed in code, as `FunctionOptions` given
to `AddFunction`, which suits values the app reads from configuration;
[Functions and triggers](/inngest-dotnet/guides/functions-and-triggers/#code-first-or-attributes) shows both forms.

<Aside type="tip">
Keep the app id and the function id stable. Inngest knows this function as `shop-onboard-user`; renaming it
creates a new function.
</Aside>

## 4. Run it

<Steps>

1. Start the app in dev mode. `INNGEST_DEV=1` points the SDK at the local dev server:

   <Tabs syncKey="shell">
   <TabItem label="bash">

   ```bash
   INNGEST_DEV=1 dotnet run --urls http://localhost:5280
   ```

   </TabItem>
   <TabItem label="PowerShell">

   ```powershell
   $env:INNGEST_DEV = "1"; dotnet run --urls http://localhost:5280
   ```

   </TabItem>
   </Tabs>

2. Start the dev server and point it at the app. Use the install script or Homebrew on macOS and Linux, npx when
   Node.js is installed, Docker when it is not, and Compose when a team shares the setup:

   <DevServer />

3. Sign up a user:

   ```bash wrap
   curl -X POST http://localhost:5280/signup -H 'Content-Type: application/json' -d '{"email": "ada@example.com"}'
   ```

4. Open `http://localhost:8288` and select **Runs**. The run shows `send-welcome-email`, the sleep, and after
   30 seconds `send-tips`.

</Steps>

## What happened

Inngest called the app four times for that one run, once per step and once more for the output:

That is why side effects belong in steps and why step ids must not change while runs are in flight.
[Steps](/inngest-dotnet/guides/steps/) explains both, and [How it works](/inngest-dotnet/how-it-works/) lets you step
through a run.
