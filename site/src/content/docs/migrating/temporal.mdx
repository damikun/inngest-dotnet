Temporal and Inngest both run durable code: a function that survives restarts, retries what failed, sleeps for days
and waits for input from outside. The programming models are close. The difference is in how the code is run.

- **Temporal** runs a workflow in a worker that polls a task queue. The workflow is replayed from its event history,
  and the SDK runs it on a deterministic task scheduler, so the whole workflow method must be deterministic.
  Activities run separately, scheduled by the workflow.
- **Inngest** calls the function over HTTP at an endpoint your app serves, or through a
  [Connect](/inngest-dotnet/guides/connect/) worker that holds a connection open. Each call runs the function from
  the top. Steps that are done return their saved results; the first new step runs, and the call ends. The code
  between steps runs on every call, but on the ordinary .NET scheduler: `Task.WhenAll`, `ConfigureAwait` and
  ordinary `async` code are fine.

So a workflow becomes a function, and each activity call becomes a step whose handler is the activity's body.

## The names side by side

| Temporal .NET | inngest-dotnet |
|---|---|
| `[Workflow]` class with a `[WorkflowRun]` method | A class that derives from `InngestFunction<TEventData>` or `InngestFunction<TEventData, TResult>` and overrides `ExecuteAsync`. See [Functions and triggers](/inngest-dotnet/guides/functions-and-triggers/). |
| Workflow arguments | The data of the event that starts the run, `context.Event.Data`. |
| `[Activity]` method, `Workflow.ExecuteActivityAsync(...)` | `context.Step.RunAsync("id", ct => ...)`. The handler is the activity's body; services come from the function's constructor, or from a scope of the step's own with `RunScopedAsync`. See [Steps](/inngest-dotnet/guides/steps/). |
| `ActivityOptions.RetryPolicy` | `Retries` on `[InngestFunction]`, which applies to each step. Inngest chooses the backoff. See [Errors and retries](/inngest-dotnet/guides/errors-and-retries/). |
| `ApplicationFailureException` with `nonRetryable: true` | `NonRetriableException`. `RetryAfterException` sets the time of the next attempt. |
| `Workflow.DelayAsync(...)` | `context.Step.SleepAsync("id", duration)` or `SleepUntilAsync`. |
| `[WorkflowSignal]` and `Workflow.WaitConditionAsync(..., timeout)` | `context.Step.WaitForSignalAsync` or `WaitForEventAsync`, both with a timeout. See [Signals and waits](#signals-and-waits). |
| `[WorkflowQuery]` | No query into a running function. Publish its state with [Realtime](/inngest-dotnet/guides/realtime/), or save it in a step. |
| `[WorkflowUpdate]` | No direct match. See [Where there is no direct match](#where-there-is-no-direct-match). |
| `Workflow.ExecuteChildWorkflowAsync(...)` | `context.Step.InvokeAsync<TFunction, TResult>(...)`. See [Invoking functions](/inngest-dotnet/guides/invoking-functions/). |
| `Workflow.StartChildWorkflowAsync(...)` without awaiting the result | `context.Step.SendEventAsync(...)` with an event the other function runs on. |
| `Workflow.WhenAllAsync`, `Workflow.WhenAnyAsync` | `Task.WhenAll` and `Task.WhenAny` over steps, or `ParallelAsync(ParallelMode.Race, ...)`. See [Parallel steps](/inngest-dotnet/guides/parallel-steps/). |
| `Workflow.UtcNow`, `Workflow.NewGuid()`, `Workflow.Random` | Read the value in a step: `await context.Step.RunAsync("now", () => DateTimeOffset.UtcNow)`. |
| `Workflow.Logger` | `context.Logger`, which stays quiet while the function replays. |
| `Workflow.CreateContinueAsNewException(...)` | Send an event that starts a new run from a step, then return. |
| `Workflow.Patched(...)` | No patch API. Steps are matched by id; see [Changing a function](#changing-a-function). |
| `TemporalClient.StartWorkflowAsync(...)` | `IInngestClient.SendAsync(...)` with an event. See [Sending events](/inngest-dotnet/guides/sending-events/). |
| `WorkflowOptions.Id` as a dedupe key | The event's `Id`, `Idempotency` on `[InngestFunction]`, or `[Singleton]`. |
| `handle.GetResultAsync()` | `IInngestRunsClient.GetEventRunsAsync(eventId)`, then `GetRunAsync(runId)` for the status and output. |
| `handle.CancelAsync()`, `TerminateAsync()` | `IInngestRunsClient.CancelRunAsync(runId)`, or `[CancelOn]` to cancel on an event. |
| `AddHostedTemporalWorker(...)`, task queues | `AddInngest(...)` and `app.MapInngest(...)`, or `AddConnect(...)` for a worker with no public endpoint. |
| Schedules (`CreateScheduleAsync`) | `[CronTrigger]` on the function. |
| `WorkflowEnvironment.StartTimeSkippingAsync()` | `InngestTestHost` from `Inngest.Testing`, which runs on a simulated clock. See [Testing](/inngest-dotnet/guides/testing/). |
| `WorkflowReplayer` | No match. |

## A workflow and its activities

{/* check: skip */}
```csharp title="Temporal .NET"
[Workflow]
public class OrderWorkflow
{
    [WorkflowRun]
    public async Task<string> RunAsync(Order order)
    {
        var paymentId = await Workflow.ExecuteActivityAsync(
            (OrderActivities a) => a.ChargeAsync(order),
            new() { StartToCloseTimeout = TimeSpan.FromMinutes(5), RetryPolicy = new() { MaximumAttempts = 5 } });

        await Workflow.DelayAsync(TimeSpan.FromMinutes(10));

        await Workflow.ExecuteActivityAsync(
            (OrderActivities a) => a.SendReceiptAsync(order, paymentId),
            new() { StartToCloseTimeout = TimeSpan.FromMinutes(1) });

        return paymentId;
    }
}

public class OrderActivities(IPaymentGateway payments, IEmailSender email)
{
    [Activity]
    public Task<string> ChargeAsync(Order order) =>
        payments.ChargeAsync(order.CustomerId, order.Total, ActivityExecutionContext.Current.CancellationToken);

    [Activity]
    public Task SendReceiptAsync(Order order, string paymentId) =>
        email.SendAsync(order.CustomerId, $"Receipt for {paymentId}", ActivityExecutionContext.Current.CancellationToken);
}
```

```csharp title="inngest-dotnet"
using Inngest;

[InngestFunction("process-order", Retries = 4)]
[EventTrigger<OrderPlaced>]
public sealed class ProcessOrder(IPaymentGateway payments, IEmailSender email) : InngestFunction<OrderPlaced, string>
{
    public override async Task<string> ExecuteAsync(FunctionContext<OrderPlaced> context, CancellationToken cancellationToken)
    {
        var order = context.Event.Data;

        var paymentId = await context.Step.RunAsync("charge",
            ct => payments.ChargeAsync(order.CustomerId, order.Total, ct));

        await context.Step.SleepAsync("cool-off", TimeSpan.FromMinutes(10));

        await context.Step.RunAsync("send-receipt",
            ct => email.SendAsync(order.CustomerId, $"Receipt for {paymentId}", ct));

        return paymentId;
    }
}
```

`Retries = 4` gives every step up to five attempts, as `MaximumAttempts = 5` does. The function's class gets its
services from dependency injection, as an activities class does with `AddScopedActivities`. A step that needs a
scoped service of its own, such as a `DbContext`, takes it with
[`RunScopedAsync`](/inngest-dotnet/guides/scoped-steps/).

Each step has an id. Inngest saves the step's result under it, and the id must stay the same between deploys while
runs are in flight. Temporal identifies activities by their order in the history instead. The
[step analyzers](/inngest-dotnet/guides/source-generator/#check-steps-for-replay-safety) report ids that would
change between calls.

Starting it is sending the event:

{/* check: skip */}
```csharp title="Temporal .NET"
var handle = await client.StartWorkflowAsync(
    (OrderWorkflow wf) => wf.RunAsync(order),
    new(id: $"order-{order.OrderId}", taskQueue: "orders"));
```

{/* check: statements; IInngestClient inngest; OrderPlaced order; CancellationToken cancellationToken */}
```csharp title="inngest-dotnet"
var sent = await inngest.SendAsync(new InngestEvent(OrderPlaced.EventName, order)
{
    Id = $"order-{order.OrderId}",
}, cancellationToken);
```

The event `Id` makes a second send of the same order start no second run, which is what a workflow id is often used
for. A function can also run on several events and on a schedule, and several functions can run on one event.

## Signals and waits

A Temporal workflow receives a signal in a handler method, which sets a field, and waits for the field with
`WaitConditionAsync`. An Inngest function waits for the signal itself, in a step that returns its data, or `null`
when the timeout passes.

{/* check: skip */}
```csharp title="Temporal .NET"
private bool approved;

[WorkflowSignal]
public async Task ApproveAsync() => approved = true;

// In the run method:
if (!await Workflow.WaitConditionAsync(() => approved, TimeSpan.FromDays(1)))
{
    return "timed-out";
}
```

{/* check: body OrderPlaced */}
```csharp title="inngest-dotnet"
var approval = await context.Step.WaitForSignalAsync("wait-for-approval",
    new WaitForSignalOptions($"approve-order/{context.Event.Data.OrderId}", TimeSpan.FromDays(1)));

if (approval is null)
{
    return "timed-out";
}
```

Code outside the function sends the signal by its name:

{/* check: skip */}
```csharp title="Temporal .NET"
await client.GetWorkflowHandle<OrderWorkflow>($"order-{orderId}").SignalAsync(wf => wf.ApproveAsync());
```

{/* check: statements; IInngestClient inngest; string orderId; CancellationToken cancellationToken */}
```csharp title="inngest-dotnet"
var runId = await inngest.SendSignalAsync(new InngestSignal($"approve-order/{orderId}"), cancellationToken);
```

Two differences matter:

- **A signal is not kept for later.** Temporal records a signal in the workflow's history even when nothing waits for
  it yet. An Inngest signal resumes the run that is waiting for it at that moment; `SendSignalAsync` returns `null`
  when no run waits. Wait early, or check in a step whether the thing already happened.
- **Events are the broadcast form.** `WaitForEventAsync` waits for an event that matches an expression, such as the
  same order id. Any number of runs can wait for matching events, and the same event can also start other
  functions. It too sees only events that arrive after the wait starts. See
  [Sleep and wait for events](/inngest-dotnet/guides/sleep-and-wait-for-events/).

## Queries become published state

There is no way to call into a running Inngest function. Report its state as it goes instead: publish it with
[Realtime](/inngest-dotnet/guides/realtime/) to the clients that watch it, or write it to your database in a step for
clients that ask later.

{/* check: skip */}
```csharp title="Temporal .NET"
[WorkflowQuery]
public string Status { get; private set; } = "received";
```

{/* check: body OrderPlaced */}
```csharp title="inngest-dotnet"
var status = new RealtimeTopic<string>($"order:{context.Event.Data.OrderId}", "status");

await context.Step.PublishAsync("publish-received", status, "received");
```

`IInngestRunsClient.GetRunAsync` gives a run's status, such as `Running` or `Completed`, and its output once it has
ended.

## Child workflows

{/* check: skip */}
```csharp title="Temporal .NET"
var score = await Workflow.ExecuteChildWorkflowAsync(
    (ScoreAccountWorkflow wf) => wf.RunAsync(new ScoreRequest(accountId)));
```

{/* check: body JsonElement; string accountId */}
```csharp title="inngest-dotnet"
var score = await context.Step.InvokeAsync<ScoreAccount, AccountScore>("score-account",
    new ScoreRequest(accountId), timeout: TimeSpan.FromHours(1));
```

The invoked function runs as a run of its own, with its own retries and history. Its result comes back as the step's
result, typed by the compiler from `ScoreAccount`'s base class.

## Compensation

Temporal's .NET SDK has no saga helper either; the usual pattern keeps a list of compensations and runs them in a
`catch`. The same pattern works with steps. When a step has used all its attempts, awaiting it throws
`StepFailedException`, and the compensations are steps too:

{/* check: body OrderPlaced; IInventory inventory; IPaymentGateway payments */}
```csharp title="inngest-dotnet"
var order = context.Event.Data;

var reservationId = await context.Step.RunAsync("reserve-stock",
    ct => inventory.ReserveAsync(order.OrderId, ct));

try
{
    await context.Step.RunAsync("charge-card", ct => payments.ChargeAsync(order.CustomerId, order.Total, ct));
}
catch (StepFailedException exception)
{
    await context.Step.RunAsync("release-stock", ct => inventory.ReleaseAsync(reservationId, ct));
    throw new NonRetriableException($"Payment failed: {exception.Error.Message}", exception);
}
```

See [Recover from a failed step](/inngest-dotnet/guides/errors-and-retries/#recover-from-a-failed-step).

## Determinism

Temporal asks the whole workflow method to be deterministic, and gives you `Workflow.UtcNow`, `Workflow.NewGuid()`,
`Workflow.Random` and its own task helpers. In an Inngest function the rule is narrower: everything that is not the
same on every call goes into a step.

- Side effects, such as I/O, emails and database writes, go in steps. Code outside a step runs on every call.
- Values that change between calls, such as the time, a new id or a random number, come from a step, which saves
  them: `var now = await context.Step.RunAsync("read-clock", () => DateTimeOffset.UtcNow);`
- Step ids are constants, or built from event data, step results and loop indexes.
- `Task.WhenAll`, `Task.WhenAny`, `ConfigureAwait(false)` and `Task.Run` inside a step handler are fine. Do not
  start a step from inside another step's handler.

## Changing a function

Temporal's `Workflow.Patched` keeps old and new code side by side while old runs finish. Inngest has no patch API.
A run that is in flight when you deploy continues on the new code: steps it already ran return their saved results
by id, and steps it has not reached run as the new code says. So:

- Adding a step, or changing code after the steps a run has done, is safe.
- Renaming a step id makes in-flight runs run that step again.
- A change that must not reach old runs goes into a new function, with a new id, while the old one drains.

## Where there is no direct match

- **Updates.** `[WorkflowUpdate]` sends a request into a running workflow and returns its answer. The closest form
  is a signal that the function waits for, with the answer published through
  [Realtime](/inngest-dotnet/guides/realtime/). For a request that should run durable steps and answer the caller
  itself, see [durable endpoints](/inngest-dotnet/guides/durable-endpoints/).
- **Per-activity timeouts.** Activity options set start-to-close and heartbeat timeouts per call. Steps have no
  timeout of their own: put the timeout in the handler, such as `HttpClient.Timeout`, and limit the whole run with
  `[Timeouts]`. A step must also finish within one request from Inngest to your app, so long work is split into
  steps. See [Flow control](/inngest-dotnet/guides/flow-control/#timeouts).
- **Per-activity retry policies.** The number of retries is set per function. Inngest chooses the backoff, and
  `RetryAfterException` sets the time of one retry.
- **Continue-as-new.** An Inngest run has limits on its number of steps and the size of its state; see Inngest's
  [limits](https://www.inngest.com/docs/durable-execution/limits). For a loop that never ends, send an event from a step
  that starts a new run with the state it needs, and return.
- **Replay testing.** There is no `WorkflowReplayer`. Unit tests run functions on `InngestTestHost`, and
  [Testcontainers](/inngest-dotnet/guides/testing-with-containers/) runs them end to end against the dev server.
- **Listing and searching workflows.** There are no search attributes, and the SDK's runs client gets a run by id or
  by the event that started it. The Inngest dashboard lists and filters runs.
